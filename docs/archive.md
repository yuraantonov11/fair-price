# Приватний архів підтверджених цін

Архів: **приватний** `yuraantonov11/fair-price-archive`. Основний репозиторій і runner залишаються публічними; архівні файли не публікуються в логах, CI artifacts або розширенні. Жодних платних сервісів чи нових runtime-залежностей.

## Одноразове налаштування

1. GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens: створіть token для **лише** `fair-price-archive`, Repository permissions → **Contents: Read and write**. Встановіть строк дії та поновлюйте його до завершення. Не використовуйте загальний token до всіх репозиторіїв.
2. У **основному** `fair-price` додайте Actions secret `PRICE_ARCHIVE_TOKEN`. Не надсилайте його в чат, не додавайте в Git або змінні `VITE_*`.
3. Actions variables: `PRICE_ARCHIVE_REPO=yuraantonov11/fair-price-archive`, `PRICE_ARCHIVE_PRUNE=false`. Наявні `SUPABASE_URL` і `SUPABASE_SERVICE_ROLE_KEY` використовуються лише сервером.
4. Застосуйте всі SQL-міграції в порядку імен. Щоденний workflow спочатку запускає `npm run archive`, потім crawler. Обидва використовують той самий database lease, що й Edge.

## Формат і збереження

Supabase зберігає щонайменше 90 календарних днів. Архівуються лише завершені UTC-місяці, кінець яких не пізніший за UTC-сьогодні мінус 90 днів. Частковий старий місяць залишається в БД. Поточна історія з жовтня 2026 ще не підлягає архівуванню.

Private release `prices-YYYY-MM` містить `manifest.json` та `observations-NNNN.jsonl.gz`. Кожен рядок має `product` (метадані на момент експорту) та `observation` (усі поля щоденного підтвердження, включно з недоступністю й ідентифікаторами). Ціни — цілі копійки. Повторення стискає gzip, не видалення підтверджених днів. Це експорт підтверджень, а не повна резервна копія всього Supabase: feedback, community reports і службові дані до нього не входять.

Маніфест v1 фіксує схему `20261019`, UTC-діапазон `[fromDay, untilDay)`, кількість рядків, назви, розміри та SHA-256 частин. Частини до 100 MiB. Restore використовує міграції до зафіксованої версії. `price_history` та legacy-записи залишаються в БД і не перетворюються на довірені підтвердження.

## Перевірка й увімкнення очищення

На машині власника виконайте `npm run setup` і налаштуйте server-only env. Локальна `.env` може містити ці значення, але залишається поза Git. Для перевірки вже створеного місяця:

```powershell
npm run archive:verify -- --month 2026-10
npm run archive:restore -- --month 2026-10
```

`verify` заново скачує приватні assets, перевіряє хеші, кількості, унікальність ID, одиниці та межі дат. `restore` додатково створює ізольовану PGlite/PostgreSQL БД у пам'яті, застосовує схему, відновлює оригінальні рядки та порівнює їх. У production він записує тільки доказ успішного тесту в приватний `price_archive_exports`; самі ціни в production не відновлюються. PGlite — наявна dev dependency, crawler її не встановлює.

Альтернатива локальним серверним credentials: Actions → **Verify Private Price Archive** → виберіть `verify` або `restore` та вже архівований місяць. Workflow використовує наявні GitHub secrets, не завантажує архів як CI artifact та не відновлює ціни у production.

Після успішного restore реального архіву можна встановити Actions variable `PRICE_ARCHIVE_PRUNE=true`. SQL відхиляє очищення без перевіреного маніфесту, доказу відновлення формату v1 та активного lease. Перед кожним очищенням усі файли знову скачуються й перевіряються. Видаляються лише ID з точним збігом усіх полів експортованого підтвердження. Змінені рядки залишаються; їх кількість буде видно у звіті. Приватний реєстр зберігає хеш маніфесту й кількість видалених рядків.

Невдале завантаження залишає вихідні рядки в БД. Неповний незареєстрований upload може бути перебудований; завершений маніфест і зареєстрований архів не перезаписуються. Пошкоджений завершений архів вимагає втручання власника; автоматичного видалення вихідних даних немає. Не видаляйте архівні releases після очищення Supabase.

## Ліміти й діагностика

- Від 400 000 000 bytes crawler обходить лише вже відомі товари; sitemap і нові community URL не розширюють каталог.
- Від 450 000 000 bytes Node та Edge припиняють записи з `STORAGE_BUDGET_EXCEEDED`. SQL triggers також захищають записи товарів, підтверджень і community reports. Видалення залишається доступним.
- Розмір вимірюється через `pg_database_size`, включно з індексами та зайнятим місцем таблиць. DELETE не гарантує негайного зменшення файлів: autovacuum може зробити місце придатним для повторного використання. Якщо захисний поріг залишається перевищеним, власник має перевірити bloat/дисковий обсяг у Supabase; автоматичного `VACUUM FULL` немає.
- Семиденне очищення community reports не зачіпає підтверджену історію. CI artifacts живуть сім днів; архіви зберігаються в приватних release assets.
- Підсумок Actions показує бюджет, стан архіву та кількості. Відсутній token або помилка архіву залишають очищення безпечним; crawler продовжує роботу в межах бюджету. Фактичний egress контролюється в Supabase Dashboard, а не оцінюється як точний за кількістю рядків.
- Безкоштовні квоти й GitHub schedule не дають гарантії безперервності: schedule може запізнюватись або вимикатись через тривалу неактивність репозиторію. Віджет показує час останнього підтвердження та застарілість.

## Перехід публічного API

Спочатку розгортається додаткова міграція та клієнт 2.5.0. Після успішної публікації `v2.5.0` release workflow викликає `archive:announce-release`: починається 14-денний період оновлення старих клієнтів. Повторний виклик його не подовжує. До релізу відлік не запускається.

Щоденний maintenance після цього строку викликає `apply_history_privacy`: прямі SELECT до `products`, `price_history`, `price_observations` закриваються, `get_product_history(p_url)` продовжує віддавати максимум 60 довірених доступних днів одного товару. Власник також може запустити `npm run archive:privacy`; до завершення строку воно поверне `restricted: false`. Старі розширення після переходу потребуватимуть оновлення.

Приватність архіву не обмежує повторне збирання даних, які відкритий API віддає розширенню. Раніше оприлюднені копії даних також неможливо відкликати.
